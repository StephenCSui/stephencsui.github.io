XR Teleoperation

This was a university group project to let a VR headset control a robot arm that draws on a real canvas, translating what you draw in Unity into real strokes from a physical UR3 arm. My part was the XR side. I got a Meta Quest 2 controller driving the arm, with full control over both the simulated and physical hardware. I built the control pipeline end to end, using a custom authority filter and MoveIt Servo.

VR teleop driving the real UR3 to draw on the canvas, live at a lab demo.

What it does now

Hand pose from a Quest 2 controller in Unity drives a real UR3 arm through MoveIt Servo, via an authority filter handling anchor-based delta control, workspace clamping, and mode switching. NORMAL mode gives full-range teleop. PRECISION mode tightens the gains for close-up work, with a detach-and-nudge mode for fine discrete positioning. Orientation snap aligns the controller and end-effector frames on startup so the mapping feels natural in VR. On the Unity side, a virtual canvas mirrors each stroke as you draw, and a precision bounding box you can resize sets how fine that close-up control gets.

Close-up PRECISION-mode control on the real arm, the last clip recorded for this project.

Timeline

  1. ROS-TCP-Connector set up in Unity; hand pose publisher and keyboard toggle built.
  2. High latency from the MoveIt planning cycle, and goal rejection when the hand moved too fast, not suitable for real-time teleop. Planning was dropped in favor of direct servo control.
  3. Replaced planning with MoveIt Servo; built a P-controller and a C++ authority filter for safety gating, workspace limits, and deadbands.
  4. Default arm pose hit singularities immediately on any movement. YAML tuning didn't help, fixed by changing the starting joint configuration instead.
  5. forward_velocity_controller kept defaulting inactive on startup. Set it as the default active controller in the launch arguments as a first fix.
  6. That wasn't enough on its own, since MoveIt Servo also needed a reset/start/unpause sequence on every connection to the robot. Wrote servo_auto_start, a one-shot bootstrap node that does the whole sequence automatically at launch, gated on the robot's own "program running" signal.
  7. First confirmed keyboard-driven control in simulation via servo.
  8. Validated the full pipeline in URSim (Docker) before moving to physical hardware.
  9. Wrong launch order left the velocity controller inactive. servo_auto_start was using a normal subscription and missed the robot's startup signal if it had already fired before the node subscribed. Fixed with a transient-local subscription so it always catches the robot's current state regardless of order.
  10. Gains were too aggressive for real hardware, causing oscillation and overshoot. Retuned down significantly.
  11. Missing settle delay meant the hand anchor latched before Unity finished its position snap, teleporting the arm on teleop enable. Fixed with a short delay.
  12. First confirmed control on physical UR3 hardware.

    The pipeline working end to end, demoed in front of the rest of the lab.

  13. Added PRECISION mode: position sensitivity scaled down significantly compared to NORMAL, with its own tuned deadband and step limits for close-up work.
  14. Precision bounding box drawn in Unity drives position scale. Smaller box, finer control.
  15. Detachment + nudge mode: suspends hand tracking, discrete button presses nudge position/orientation instead.
  16. Position snap to the controller worked, but orientation snap was missing. Controls felt sideways depending on starting angle.
  17. Implemented orientation snap on startup so the tracking origin faces a fixed known direction toward the robot.
  18. Adjusted the wrist joint for a natural end-effector orientation matching VR controller ergonomics.
  19. APK built for Quest 2. End-to-end servo pipeline confirmed working in VR.
  20. PRECISION entry gate widened, was too tight to enter reliably near the canvas.
  21. PRECISION mode toggle made global, no longer gated on being near a specific position.

Difficulties

01 Failure log

The default pose was already broken

The arm started every session in its default pose, straight down. The moment servo control tried to move it from there, it hit a singularity and refused to respond. Tuning the servo YAML's singularity thresholds and condition number limits did nothing. The real fix was starting the arm from a different joint configuration that wasn't singular in the first place, and that choice of starting pose stuck around as a hard constraint for every later fix that touched the robot's starting angles.

02 Failure log

A controller that wouldn't stay active

MoveIt Servo would report itself as active right after launch, but that status was misleading, trying to actually drive the arm through it did nothing, since it hadn't really been started. Getting it truly running meant explicitly resetting, starting, and unpausing servo through its own services, not just trusting what it reported. forward_velocity_controller needed to be switched active too, and none of this happened automatically, so a bootstrap script, servo_auto_start, was built to do all of it in one shot at launch, gated on the robot's own "program running" signal. That gate was initially unreliable, it used a normal subscription, so if the robot had already started before the node subscribed, it missed that already-published signal and just timed out, leaving the controller inactive. Fixed by subscribing with a transient-local QoS profile, so it always catches the robot's current state regardless of which started first.

03 Failure log

Tuning for a real arm, not a simulated one

Gains that worked fine in simulation caused visible oscillation and overshoot the moment the pipeline ran against the physical UR3. URSim's simulated arm just followed commands instantly; the real one had actual actuator latency, so the same gain that looked stable in simulation overshot and corrected on real hardware instead of settling. Fixed by reducing the linear gain and the arm's max speed substantially, rather than assuming sim-tuned values would carry over.

04 Failure log

A teleport on every teleop enable

Enabling teleop made the arm jump instantly instead of smoothly picking up from where the hand was, the same symptom as half the other bugs on this list, so it wasn't obviously a timing issue at first. It turned out the filter was latching its anchor the moment teleop was enabled, before Unity had finished snapping the hand into position, so the anchor was captured from a stale pose. Fixed with a short settle delay before the anchor is latched.

05 Failure log

Controls felt sideways in VR

Position tracking worked, but the controller's forward direction didn't reliably map to the arm's forward direction, depending on which way the headset was facing at startup, forward and sideways could get swapped. Position snap alone wasn't enough; the fix was adding an orientation snap on startup that turns the tracking origin to face a fixed known direction toward the robot, so the mapping stays consistent no matter which way the player is facing when they start.

06 Failure log

Getting the canvas plane and start pose to agree

Moving the canvas stop/touch planes closer to the robot without checking anything else would have made the arm jerk backward the instant teleop was enabled, since its own starting position was already past the new stop plane. Fixed by recalculating the starting joint angles so the end-effector's starting position stayed safely behind the plane, and writing that down as a standing rule to check any time either value changes again.

A related bug meant PRECISION mode's simulated pen-down motion moved the wrong way entirely, a sign error sent the virtual hand target away from the canvas instead of toward it, so the arm barely moved on pen-down at all. Fixed by correcting the sign and increasing the push distance so it reliably overshoots into the plane clamp instead of falling short.

07 Failure log

Getting the canvas to actually draw

Getting virtual drawing working on the canvas meant clearing a handful of separate issues. The raycast used to represent the pen tip needed real tuning to land on the canvas consistently instead of passing straight past it. PRECISION mode had a control axis inverted at one point. Painting still looked wrong even once the ray was landing, since the canvas's collider type doesn't return valid UV data through Unity's raycast hit info, fixed by rebuilding the UV mapping from the raycast hit's position directly.

08 Failure log

A raycast that skipped its own target

After rescaling the canvas-drawing collider down, drawing stopped registering. The raycast used for painting was being cast from a point that used to sit inside the collider, and a raycast never registers a hit against the collider it starts inside of. Shrinking the collider moved the ray's starting point outside it, so the ray now hit a different collider first instead. Fixed by testing the canvas collider directly instead of relying on a general-purpose raycast.

09 Failure log

A robot that was rotated 180° from the math

The physical UR3 was mounted rotated 180° around its base from what the original software assumed. That rotation got propagated into the ROS launch config, workspace bounds, canvas plane values, but not into the actual Unity-to-ROS coordinate conversion formulas. So the position and rotation math in the C++ authority filter, and in three separate Unity scripts, was all using the wrong sign conventions at once. Re-derived the conversion formulas for the rotated frame from scratch and updated all of them together, since fixing only one would have just moved the mismatch somewhere else.

10 Failure log

Silent failures from lost Unity wiring

Merging my Unity project with a teammate's surfaced a batch of script references that had gone null, editor field assignments neither of us could have caught while working in isolation. None of it threw an error, the affected code just silently did nothing. The XR snap never fired because its target reference was null. Two of the visualization boxes sat frozen at the world origin regardless of what the real robot was doing, because their reference fields were null too. On top of that, a flag controlling when the control filter was allowed to lock onto its target had been left in the wrong state, so it was locking on before the XR snap even happened, chasing a target over a meter away from the real robot the entire time. Fixed by re-wiring every null reference and restoring that flag.

Current status

End to end, the system works on real hardware, a Quest 2 controller drives a physical UR3 arm through MoveIt Servo, with NORMAL and PRECISION modes plus a detach-and-nudge mode for fine positioning. Canvas plane calibration and the PRECISION pen-down behaviour are tuned and working for the current physical setup.

What's unfinished is integration, not the control pipeline itself. I spent most of my time getting my own subsystem solid and assumed combining it with the rest of the team's work would be straightforward, since the interfaces between them were well defined on paper. That assumption was wrong. Merging the Unity projects surfaced missing scene references neither of us could have caught in isolation, and some hardware quirks only showed up on certain machines. I should have been integrating in parallel with my own work the whole time, instead of treating it as a separate phase to handle once everything else was done.

Acknowledgements & tools

This was a 3-person university group project. My part was the XR and control side described on this page, the ROS2 authority filter, servo control, precision/detachment modes, and the Unity-side scripts driving them. A teammate built the camera-based canvas pose detection system; another built the Unity environment. Neither is described here since it isn't my work.

Built with ROS2 and MoveIt Servo (real-time arm control), Unity and the ROS-TCP-Connector (XR operator interface and the bridge to ROS), a UR3 robot arm with URSim and Docker (hardware and simulation), and a Meta Quest 2 headset via OpenXR (VR runtime).
