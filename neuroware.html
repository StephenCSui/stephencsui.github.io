NeuroWare

This is a personal project built around Isaac Sim, using Nav2 as its primary navigation library. Isaac Sim stood out for its AI capabilities, which tools like Gazebo don't offer to the same extent. Designing and training my own AI is something I want to look into later on. I'd used Isaac Sim briefly on a university project before and wanted to go further with it on something of my own.

Perspective

Milestone 1: full pickup-to-drop-off run, sped up 4x.

What it does now

The current version is capable of moving a sequence of three objects, one at a time, between shelves. What it's carrying changes how it acts during navigation, with different shapes and weights calling for different behaviour around obstacles. The hope is to have robot-to-robot cooperation working in a future implementation, for objects too heavy or complex for a single robot to handle alone.

Timeline

This project changed direction twice before settling on its current form. It started as a swarm of robots pushing items across a warehouse floor, then pivoted to a farming swarm, since farming seemed like a wider, more broadly useful application. Over time it became clear that swarms, in their current form, aren't that effective, largely because of hardware: swarm units tend to be heavier and more expensive than expected, and most of what a swarm is supposed to offer can generally be matched more cheaply with fixed infrastructure instead, like signal poles. Running real AI on a swarm is difficult too, since you want a large number of units, but each one still needs to be powerful enough to actually run it. I wanted to focus on learning what already works and actually understanding it.

Difficulties

01 Failure log

A constant hardware constraint

GPU memory on this hardware is an ongoing constraint. Using default settings outright isn't possible, and since the whole point of this project is getting familiar with Isaac Sim, that's something that needs to be worked around constantly rather than solved once. In practice that means constantly finding lower-memory ways to do the same thing, cutting anything that isn't strictly necessary, and swapping components for cheaper alternatives when one turns out too expensive.

02 Failure log

A reflex that couldn't tell it had failed

The first version of obstacle handling was reactive, and would only turn and move at fixed distances once it detected something in its path. The real problem wasn't the reflex itself, it's that it had no way of telling it had failed. In one such case it turned straight into a shelf leg and got stuck. It was unable to recognize it was stuck or attempt a different approach. As this was early development, the system was eventually replaced with an occupancy-grid + A* planner, giving the robot actual decision making instead of a fixed reaction.

03 Failure log

Migrating to Nav2

The planner built to fix the reactive-dodge problem had a bug of its own. It kept a live map of what was around the robot, but when it spotted something close and stopped, that sighting never got written into the map. So the next time it planned a route, it didn't know that spot was blocked, and picked the same route into the same obstacle again.

Even after that bug got fixed, the planner had failed live enough times that continuing to patch it stopped making sense. The navigation system was migrated to Nav2 instead, ROS2's own navigation stack.

The migration wasn't simple either. The first attempt tried running ROS2 directly inside Isaac Sim's own Python process, and it crashed immediately. The cause was a mismatch between Python versions: Isaac Sim's Python and the ROS2 library it needed to talk to were each built for a different one, and that broke the moment a real ROS2 message got created. It wasn't fixable by changing a setting, it needed a different approach entirely.

The fix was switching to Isaac Sim's own built-in bridge instead, which talks to ROS2 without going through that broken path. Once that was working, a separate bug turned up in how goal positions were calculated: an offset wasn't accounting for the robot's own starting rotation, which put a goal marker almost 4 meters from where it should have been.

The Nav2 implementation allowed the robot to complete a full transport run while avoiding an obstacle placed in front of its optimal path.

04 Failure log

A fight between two motors

The robot is based on a modified version of a robot in a published paper. During turns, the plate's own motor which actively counter-rotates it to keep whatever it's carrying facing the same direction, was found to be interfering with the wheels' own speed control. This was confirmed by testing the robot completely empty, no cargo, no obstacles, and finding the same instability still happened. The first fix tried was lowering that motor's strength, tested at several levels all the way down to zero, but none of them helped, which showed the problem wasn't the strength, it was that the motor was actively driven at all. Fixed by disabling the plate's joint outright during a turn, letting it hold still under its own weight, then re-enabling it once the turn finished.

05 Failure log

A safety margin off by 1.3cm

During a carry route, the robot got stuck detecting the same obstacle in a loop. Once it stopped, it would replan a route, and immediately detect the same obstacle again. The stop distance had been calculated from the robot and object's size, and it landed just 1.3cm past a reading the sensor gave off on its own, so the robot always read that as too close.

The first fix set the stop distance to exactly match the planner's own safety margin. That stopped the loop, but broke planning instead. The robot now stood right on the planner's boundary, which looked like a collision to it, so it refused to plan any route at all.

The real fix was to set the stop distance from what the camera actually reported near the boundary, instead of calculating it from geometry, and leave enough gap between that and the safety margin for the planner to work with.

06 Failure log

Getting reliable ranging, ending in PhysX

The first attempt at obstacle ranging used a single camera. A real lidar sensor was considered next for full coverage, but was rejected since it cost too much memory compared to a camera. The setup was changed to 4 cameras, one on each corner, acting like a lidar around the whole robot. This worked well enough to get through Milestone 1. Later, an attempt was made to calibrate the camera readings against a real lidar sensor as ground truth, but the lidar sensor itself gave inconsistent readings run to run. The whole approach was replaced with PhysX raycasting instead, which turned out to be cheaper, consistently accurate, and effectively acts as a simulated lidar.

07 Failure log

Cargo dropping mid-carry

An object falling off mid-carry was a recurring bug that took several rounds to actually solve. The first guess was that the robot's heading drifted slightly off course over the drive, and the object slowly slid off as a result. That was wrong. Testing showed the object fell almost immediately, within a few seconds of starting to move, which pointed to something happening right at the start of the drive, not a slow drift.

A separate bug, where the robot stopped in the wrong spot, was first assumed to be caused by the same attachment problem, but turned out to be an unrelated bug in the stop-condition logic.

The real cause of the drop was the robot accelerating at full speed the instant it started moving from a dead stop, right after a lift. Lighter objects couldn't stay seated on the plate through that kind of jolt. The fix scaled how gently the robot accelerated based on the real weight of whatever it was carrying, easing lighter objects into motion more gently while leaving heavier ones on the original fast ramp. That fix relied on reading each object's real mass directly from the simulation.

Current status

Right now the robot moves objects one at a time from one shelf to another on its own. It can plan around obstacles ahead of time, and reacts on the spot if one appears without warning.

Main sensing is done using PhysX, as a way to imitate lidar without being too expensive. Lidar itself was tested in an earlier session, but was opted out due to memory cost.

Navigation is primarily driven using Nav2, moving between a sequence of waypoints. Nav2's default driving behaviour curved instead of going straight, so a custom controller was built on top of it that treats turning and driving as separate steps, turning fully to face a heading before it starts moving. There's also a debug view showing the current waypoints and stop zones.

  • A shelf layout designed around maximizing either space or speed
  • Building a real physical robot for testing outside simulation (might end up doing this earlier for fun)

Acknowledgements & tools

NeuroWare's physical design is grounded in Yadav et al., “Maintaining the Level of a Payload carried by Multi-Robot System on Irregular Surface”. The reference actuator is a centred piston lift with a ball-joint contact plate that conforms to angled surfaces, on a skid-steer base.

Getting that design to actually work for a warehouse pick-and-carry task took real adaptation. The piston needed real position control, not damping, to hold a static load under gravity. Damping alone only resists motion, not weight. A joint-offset bug meant the platform couldn't reach far enough down to slide under a shelf object; fixing it closed a 22cm gap to 6cm. The lift force itself needed empirical retuning. It's calibrated so three of four payload objects can be lifted solo, and the heaviest requires two robots working together. That turned a physics constraint into the reason the swarm coordination exists at all.

Built with Pygame (2D prototype and transport simulation), ROS2 and Nav2 (navigation and obstacle avoidance), NVIDIA Isaac Sim, using Omniverse Kit and PhysX (physics simulation and robot control), Pixar USD (scene/asset description), and NumPy.
